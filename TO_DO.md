# План робіт: підвищення RSS до 0.8+

**Дата аудиту:** 2026-10-10
**Ціль:** стійко отримати RSS не нижче 0.8 на `full`, не погіршивши `small`, із відтворюваним виграшем на незалежних сценаріях.

## Висновок аудиту

Найперспективніша стратегія — не «увімкнути planner» чи підкрутити один коефіцієнт, а знайти, на якому етапі критична потреба губиться: **попит → прогноз потреби → пошук джерела/маршруту → призначення ресурсу → фактичне прибуття → задоволений попит**. Для кожного дефіциту треба відрізняти відсутню потребу, невчасне замовлення, брак джерела/потужності, помилковий пріоритет і втрату після призначення.

Найсильніший сигнал у наявних результатах — поточна евристика краща за повну заміну на planner/allocator. Отже, нові компоненти слід спершу інтегрувати як контрольовану надбудову над робочою політикою, а не перемикати всю політику одним прапорцем. Точна першопричина низького RSS для `chip_le`/`chip_mat` поки не доведена: потрібні свіжі причинні траси на зафіксованому агенті.

RSS у бенчмарку нормалізує заощадження відносно наївної та clairvoyant політик, агрегує чотири harm-рівні з вагами. Тому менша сира вартість одного епізоду або більше відправленого вантажу не доводить вищий RSS. Виграш треба перевіряти на тому самому наборі епізодів і за витратами, дефіцитом, своєчасністю та ресурсними обмеженнями.

## P0 — відтворювана база та діагностика втрат

### 1. Зафіксувати точні агенти та експеримент

- [ ] Зберегти незмінні ZIP/папки поточного `agents/team_agent_receiver_overflow_v15` і робочого baseline; записати SHA-256, commit, `params.json`, Python/package lock, task, entropy, episode IDs, replay seed і налаштування CPU budget у manifest.
- [ ] Окремо отримати старі candidate/baseline ZIP з хешами `4a9f7ad…` та `0e38a29…`, якщо вони ще доступні. Не відновлювати їх лише з Git і не вважати поточне дерево еквівалентом.
- [ ] Запустити поточний агент і baseline на однакових Full-епізодах без `--quick`; зберегти повні RSS звіти, а не тільки середню сиру вартість. Встановити окрему зафіксовану Small-базу.
- [ ] Внести версію та хеш агента в кожний подальший результат; всі кандидати створювати в нових каталогах, не перезаписувати baseline.

**Готово, коли:** інший запуск на тому самому submission і налаштуваннях відтворює дії/вартість або розбіжність пояснена джерелом недетермінізму.

### 2. Додати причинну атрибуцію кожного дефіциту

- [ ] Для кожного тижня, товару й sink/регіону зберігати: початковий stock, backlog, demand, видимі arrivals і WIP, вимогу до покриття, кожне віднімання з календаря запасів, створену Need (або причину її відсутності), due week і latest-feasible-dispatch.
- [ ] Для Need фіксувати всі етапи: кандидати маршрутів; джерельний запас; дозвіл; edge/entry/fleet capacity; ETA нижньою фізичною межею та прогнозом; зарезервована кількість; виконана дія; фактичний arrival; фактично покритий попит.
- [ ] Класифікувати втрату окремо: `need_not_created`, `created_too_late`, `no_source_stock`, `no_route`, `resource_capacity`, `priority_displaced`, `late_arrival`, `action_clipped`, `arrival_not_consumed`, `overstock_or_waste`.
- [ ] Розкласти метрики за `chip_le`, `chip_mat`, `chip_le_raw`, `chip_mat_raw`, `wafer`, паливом, регіоном, тижнем і harm-рівнем. Не додавати натуральні обсяги різних одиниць.
- [ ] До звітів додати дефіцитні/невідвантажені одиниці, shed/backlog, late units і тижні, freight, tariffs, holding, inventory/write-off, кількість змінених дій та utilization спільних edge/fleet/terminal ресурсів.

**Готово, коли:** найбільша частина розриву RSS/вартості пояснена вимірюваними причинними категоріями, і кожна категорія веде до конкретного коду чи обмеження середовища.

## P1 — зміни політики з найбільшим потенціалом

### 3. Зберегти евристику, інтегрувати planner/allocator інкрементально

- [ ] Не вмикати `allocation_enabled=true` як цілісну заміну: у `agent.py` цей шлях повертає результат `DecisionPipeline` раніше від набору відомих стадій евристики (`ClosedRouteDispatch`, балансування, Sales Dispatch, Production Recovery, Fuel MPC/Release/Batch/Lookahead, Receiver Overflow та ін.).
- [ ] Зробити перший гібридний кандидат так, щоб NeedPlanner рахував часові дефіцити, але поточний dispatcher залишався виконавцем. Передавати йому тільки виміряну критичність/строк; не подвоювати потік і не створювати другий резерв того самого stock.
- [ ] В наступному окремому варіанті дозволити allocator перерозподіляти лише залишкові ресурси/обсяги після перевіреної евристики. Зберігати єдиний ledger по source stock, edge, entry, fleet і arrivals для всіх стадій.
- [ ] Порівняти baseline → тільки пріоритет Need → тільки residual allocation → обидва разом. Один фактор на порівняння; логи мають довести, які саме actions змінилися.

**Готово, коли:** жодна стадія не витрачає двічі ті самі запаси/місткість, а кандидат має позитивну парну RSS-різницю з baseline і знижує критичний дефіцит без неприйнятного зростання сукупної вартості.

### 4. Перевірити розрахунок попиту, BOM, WIP та wafer

- [ ] На свіжому Full replay розкласти для кожного Fab→OSAT→sink ланцюга готові вироби, WIP, in-transit, OSAT output, BOM raw inputs, route/transit lead time, виробничу спроможність і горизонт планування.
- [ ] Для кожної пари node/commodity перевірити спільний датований ledger: on-hand, WIP, pipeline, queue і прогнозні arrivals зараховуються рівно один раз, лише якщо прибувають до відповідного need/due week і фізично досяжні цим вузлом.
- [ ] Встановити, чому raw-wafer Need відсутня на тижнях із нульовим Fab input stock: покриття downstream stock/WIP, обсяг виробництва, route reachability, `production_horizon` чи помилка датування. Виправляти тільки підтверджену причину.
- [ ] Перевірити lead-time offset end-to-end: останній безпечний тиждень dispatch дорівнює потребі в receipt week мінус виробничий lead і маршрутний transit; Need, створена вже після цього моменту, має бути позначена недосяжною, а не виглядати як нормальна своєчасна потреба.
- [ ] Зберегти інваріантність номінального BOM до `w_scr`: це розмір часового вікна, не множник scrap/yield. Винести safety stock у явну політику й не підмішувати його в BOM чи forecast horizon.
- [ ] Перевірити `production_horizon=8` на Full проти фактичного сумарного виробничого й транспортного lead. Розширення горизонту не повинно створювати повторні Need або передчасні закупівлі.

### 5. Замкнути багатоступеневе постачання палива

- [ ] Окремо змоделювати grid→terminal потребу та upstream source→terminal replenishment для LNG/crude. Для кінцевого grid due врахувати обидва плеча й фактичний transfer lead.
- [ ] На кожному плечі зарахувати terminal/grid stock, WIP, in-transit та черги тільки один раз; upstream Need має бути на terminal, мати окремий ID і не дублювати кінцевий дефіцит.
- [ ] Перевірити джерельний запас і shared transport capacity: наявність слоту не означає, що товар можна відправити в потрібному обсязі.
- [ ] Не створювати прямого nucfuel маршруту до вузла, де його немає. Для ядерного палива окремо звірити прогноз споживання grid з автоматичним виробництвом/раціонуванням у симуляторі за межами короткого горизонту планера.
- [ ] Оцінювати `fuel_replenishment_enabled` тільки як ізольований фактор, а потім у гібриді; попередні 7-тижневі зрізи показали нижче shed, але були неповними, не мали RSS і збільшували `no_source_stock`.

### 6. Перетворити VOLL на коректний пріоритет у реальній політиці

- [ ] Перевірити одиниці `shortage_cost_per_unit_usd` для sink, grid fuel, raw input і upstream terminal Need. Невідоме значення (`None`) відрізняти від явного нуля.
- [ ] Для кожної альтернативної доставки оцінювати граничну користь: імовірно уникнений дефіцит × VOLL за часом покриття мінус freight, tariff, war premium, holding і ризик зайвого запасу.
- [ ] Пріоритет має залежати від тижня stockout, due date, backlog/втраченого попиту, replacement routes і кількості ще доступних одиниць; фіксований round-robin або множення відправки на VOLL не враховує дефіцитність спільного ресурсу.
- [ ] Перевірити глобальний розподіл через спільні bottleneck edges/fleet/terminal capacity. Локально правильний VOLL для одного Need може погіршити загальну вартість, якщо забере шлях у ще ціннішої потреби.
- [ ] Порівняти порядок Needs і allocations та показати конкретні заміни рейсів для `chip_le`/`chip_mat`; VOLL код у opt-in Allocator не впливає на production score, поки цей allocator не є частиною активної політики.

## P2 — операційні вдосконалення після коректності попиту

### 7. Планувати за фізично можливою датою, не витрачати forecast budget на безвихідні рейси

- [ ] Для кожного need обчислювати no-wait lower bound і latest dispatch. Якщо транзит вже довший за SLA, явно вибирати між пришвидшеною альтернативою, свідомим late fallback, зміною джерела/виробництва або відмовою від витратного рейсу.
- [ ] Не зсувати due week і не називати невідомий ETA своєчасним. Звітувати unknown/late окремо; прогноз черги — умовна оцінка за сьогоднішнім станом, не гарантія.
- [ ] Не збільшувати ліміт FIFO прогнозів без доказу: архівні Full late assignments і так були запізнілими за no-wait ETA. Витрачати прогноз лише там, де результат може змінити рішення.
- [ ] Перевірити clipping: тижневі execution caps іноді були нижчі за видимі action caps (архівні Small тиждень 4, Full тиждень 67). Відділити семантику action slot від фактичної weekly mark/capacity і перевірити, чи адаптація до попереднього clipping зменшує втрати.
- [ ] Залишити CPU запас під worst-case Full observations; перевірити init+act у `sbf check` для зібраного ZIP, а не лише середній час локального прогону.

### 8. Використовувати попередження й disruption-ризик лише після калібрування

- [ ] Побудувати out-of-sample reliability/backtest попереджень: частота реальної події за рівнями warning, false positive/negative, завчасність, рішення та зміна RSS/витрат.
- [ ] Не трактувати сирий warning score як ймовірність без калібрування. Резерв і зміна маршруту мають окупати їхню вартість при фактичному ризику.
- [ ] Closure-wait лишити вимкненим у standard regime: дошка приховує дати завершення, а виміряні стандартні траєкторії не змінили жодної дії. Повернутися до цього лише з оцінювачем тривалості, побудованим із доступної історії/попереджень.
- [ ] Виміряти ціну диверсифікації маршрутів: резервний шлях корисний, лише якщо додаткова плата/holding виправдані зменшеним очікуваним дефіцитом.

### 9. Налаштовувати параметри контрольованим пошуком

- [ ] Зробити схему параметрів із типами, межами, default і компонентом-власником; перевірити, що експериментальні `experiments/presets.json` відповідають поточному `params.json` (зараз вони не є надійним описом production-набору).
- [ ] Тюнити максимум одну групу за раз: sink/commodity criticality, cover/horizon, fuel release/batch, production recovery, warning, route risk. Зберігати fingerprint параметрів і список змінених ключів.
- [ ] Уникати ручних slot/node ID для Tiny/Small/Full; використовувати `config[\"spaces\"]`, topology, commodity та спостережувані обмеження.
- [ ] Оптимізувати за RSS та harm-рівнями; одночасно контролювати shortage/shed, freight, holding, inventory, clipping і CPU, щоб не купити RSS короткостроковою надмірною відправкою.
- [ ] Відхиляти складнішу політику, якщо виграш зникає на іншому seed/root або виникає лише в одному harm-рівні без загального покращення.

## Протокол експериментів і критерії прийняття

1. **Пошук:** тренувальний root `12345`, щонайменше 64 Full-епізоди. Перебирати одну зміну за раз; зберігати пари сценаріїв і traces.
2. **Відбір:** парний `sbf compare` кандидата з незмінним baseline на однакових епізодах. Не використовувати `--quick` для висновків.
3. **Незалежна перевірка:** root `67890`, щонайменше 64 Full-епізоди, із тим самим агентним budget; потім перевірити `small`. Root 0/dev використовувати лише для фінального підтвердження, не для тюнінгу.
4. **RSS gate:** кандидат має показати точковий Full RSS ≥0.8 на незалежній перевірці й позитивну парну різницю проти чинного агента; бажано, щоб 90% paired interval не включав 0. Якщо інтервал широкий, збільшити кількість епізодів, а не заявляти перемогу за середнім.
5. **Операційний gate:** `sbf check` на упакованому кандидатові для `small` і `full`; дозволені імпорти/файли, детермінований seed, коректні форми action, повний запас CPU, немає неочікуваного clipping.
6. **Причинний gate:** RSS покращився разом із логічно відповідною метрикою (наприклад, менше дорогого unmet demand для тієї ж категорії) і без компенсуючого зростання загальних витрат. Збільшення shipped volume чи кількості forecast calls не є критерієм успіху.
7. **Відтворюваність:** опублікувати manifest, хеш submission, параметри, версію lock, roots/episodes, RSS interval, cost components і CPU. Кожна логічна зміна має окрему версію/коміт.

Приклад парного порівняння за шаблонами репозиторію:

```sh
uv run sbf compare candidate baseline --task=full --episodes=64 --entropy=67890 --cpu_budget=True
uv run sbf compare candidate baseline --task=small --episodes=64 --entropy=67890 --cpu_budget=True
uv run sbf check candidate --task=full
```

Перед широким прогоном перевірити фактичні прапорці CLI через `uv run sbf compare --help`; локальні витрати часу/пам'яті та cache benchmark не включати у submission.

## Черговість виконання

1. Зафіксувати агент/score baseline і отримати актуальний Full breakdown за harm-рівнями.
2. Додати причинні traces, знайти найбільші джерела втрат у критичних товарах.
3. Виправити підтверджені помилки попиту/часу/coverage: спершу wafer+BOM/WIP і fuel terminal chain; зберегти single-use netting та `w_scr` invariance.
4. Побудувати гібрид, що зберігає робочу евристику, та під'єднати VOLL до фактичного розподілу дефіцитних ресурсів.
5. Перевірити покращення парними Full/Small прогонами; лише тоді розширювати queue/risk forecasting і шукати параметри.
6. Підтвердити RSS ≥0.8 на незалежних епізодах і root 0, перевірити ZIP та бюджет, зафіксувати результат.

## Що зараз не робити

- Не вмикати повний planner/allocator pipeline як production default на підставі коректних unit tests або зниження витрат на короткому фрагменті.
- Не збільшувати FIFO forecast budget для рейсів, які фізично не можуть встигнути.
- Не створювати вигаданий маршрут, запас, closure end date чи ймовірність попередження.
- Не додавати неявний safety stock до BOM і не множити матеріальну потребу на довжину `w_scr`.
- Не оголошувати RSS-прогрес за raw cost одного episode, кількістю відправок, кількістю forecasts або успішним `sbf check`.
- Не тюнити на root 0/dev і не перезаписувати frozen ZIP/baseline.
