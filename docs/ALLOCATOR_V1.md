# Allocator V1 — відповідність командному таску

Це уточнення реалізації Віті під отриманий таск Allocator V1. Воно замінює
правила вибору кандидатів попереднього експерименту V4, а не прогноз Маркіяна
чи каркас Нікіти. Основний модуль: `agents/team_agent/allocation.py`.

## Зіставлення вимог

| Вимога | Було до перевірки | Виправлений V1 |
| --- | --- | --- |
| 1. allocate і погоджений AllocationResult | Сигнатура й результат були; самостійно додано kind fleet_pool | Повернуто точний контракт integration. Флот обліковується всередині, діагностика через наявні reasons |
| 2. Кандидати з доступних джерел/action slots | StaticNetwork.slots_to, залишки запасу, кінцевий пункт | Збережено. Переміщення до проміжного вузла не зараховується до іншого кінцевого отримувача |
| 3. Ціна, обсяг, обмеження, due_week, ETA | Переважно ціна; невідомий ETA й закриття не блокували dispatch | Відомий умовний ETA бере участь у виборі. Невідомий ETA і поточне блокування залишають заявку unmet із причиною |
| 4. Детермінований greedy | need_order_key працював, критерій кандидата переважно cost | Порядок потреб збережено. Критерій кандидата описаний нижче й переоцінюється після кожного призначення |
| 5. Спільні ресурси | Запаси, перше ребро, флот зменшувалися спільно | Збережено. Порожній cargo padding більше не помилково вважається прихованим вантажем |
| 6. Діагностика і стандартний release | flows/unmet/reasons були; resource_usage мав новий kind | Лише погоджені види stock/edge/chokepoint_pool; overrides і release_mode залишаються None |
| 7. Обов'язкові тести | Частину сценаріїв покрито, повтор одного тижня відхилявся | Додано строки, unknown ETA, відсутність маршруту, проміжний вузол, спільний запас різних ребер і повторюваність |

## Формат і межі модулів

```python
allocator = Allocator(config, network)  # один раз на епізод
result = allocator.allocate(state, needs, observation, network)
```

Використовуються поточні `StateSnapshot` і `DeliveryNeed` з integration:
`available_stock[(node, commodity)] -> Quantity`, `quantity`, `due_week`,
`priority`, `shortage_cost_per_unit_usd`. Індекси — з config. Вихід —
погоджений `AllocationResult`; додаткові поля/види ресурсів не вводяться.
Контракт `contracts.py` збігається з integration на 48acf87.

Метод не змінює state, needs чи observation. Результати повторних викликів
не ділять масив flows. Модулі стану/потреб і frozen baseline не змінюються.
Agent підключає V1 існуючим opt-in `allocation_enabled=true`. Default policy
лишається heuristic до оцінювання повної стратегії.

## Критерій кандидата

Потреби обробляються через чинний need_order_key:
більший priority, раніший due_week, стабільний need_id.

Для кожного призначення кандидатам заново обчислюється доступний обсяг:

```text
min(залишок заявки, спостережений запас джерела,
    залишок поточної capacity першого ребра,
    залишок detour fleet / вага, якщо потрібний флот)
```

Виключаються заборонені/непідтверджено дозволені слоти, поточно закриті
маршрути, нульові фізичні потужності, порожні/невідомі джерела, невідомий ETA
і оцінене прибуття після T. Цей консервативний V1 не вгадує дату відкриття
протоки. ETA для морської лінії без прогнозу черг — None; номінальний transit
або мінімальний no-wait arrival не перетворюється на «вчасно».

Серед решти використовується лексикографічний ключ:

```text
(клас строку: умовно вчасно перед запізненням,
 freight + tariff + war premium + late_weeks * shortage_cost_per_unit_usd,
 ETA, -доступний обсяг, slot_id)
```

Всі грошові величини — USD за одиницю відповідного товару; tariff rate
перетворюється через customs value у DeliveryEvaluator. Якщо marginal shortage
cost невідомий, штраф не вигадується: лишається transport cost. Перший елемент
ключа означає, що відома вчасна доставка має перевагу над дешевою запізнілою.
Це простий задокументований критерій V1, не доведена економічно оптимальна
політика. Запізніла доставка дозволена як fallback і позначається eta_late;
вона може зменшувати пізніший backlog, але не усуває ранній lost-sales дефіцит.

ETA є умовною оцінкою за поточними даними, не гарантією виконання. Для поточного
V1 реальний evaluator знає completion прямих маршрутів; морські черги без
наданого прогнозу лишаються невідомими. Відоме майбутнє очікування треба передати
через погоджений state/forecast handoff у наступному етапі, без вигаданих нулів.
Unit-проби V3 і correction за обсягом є спрощеною оцінкою batching; це не
симуляція всіх конкуруючих майбутніх потоків.

## Облік і діагностика

Dispatch витрачає тільки доступний спостережений stock t-1. Не додаються
майбутні pipeline/supply/WIP. Після призначення зменшуються спільні баланси
source/commodity і first edge; кандидати наступних потреб бачать їх залишки.
Потужності наступних ребер/проток не бронюються: поточний нуль там робить
маршрут непридатним для цього консервативного правила, але позитивне значення
не видається за резерв у майбутньому.

Флот має спільний залишок tb/ct з консервативною оцінкою поточних автоматичних
releases. Деталі `fleet_budget_usage` і `automatic_release_fleet_bound`
передаються через існуючий DecisionReason. ResourceUsage містить тільки
погоджені види ресурсів, які allocator справді використовує; він не додає
майбутній chokepoint_pool usage для вантажу, що лише входить у морську лінію.

UnmetNeed — непризначений обсяг із причиною, зокрема delivery_eta_unknown,
currently_blocked_delivery_route, no_permitted_delivery_slot або вичерпані
ресурси. Призначений запізнілий обсяг супроводжується eta_late, а умовно
вчасний — eta_on_time_estimate. flows — кількості, не частки capacity.
Опис «вчасно» завжди умовний; allocator не звітує про фактичне майбутнє
обслуговування. Release залишений стандартним: обидва optional arrays — None.

Оновлення V2 виконується один раз на тиждень. Повтор того самого observation
використовує snapshot і заново будує незалежні бюджети. Змінений network
observation у вже обробленому тижні явно відхиляється, щоб не використати
старі обмеження мовчки. Новий тиждень оновлює history звичайним способом.

## Перевірки

```text
uv run pytest tests/test_allocation.py tests/test_team_contracts.py -q
uv run python examples/10_network_allocation.py --task=tiny
uv run python examples/10_network_allocation.py --task=small
uv run python examples/10_network_allocation.py --task=full
```

Тести покривають усі сім пунктів таску, default release, строки, explicit late
діагностику, unknown stock, blackout permission, horizon, незмінність вхідних
даних, спільний fleet і padding. Синтетичні тести морської capacity явно
передають нульову прогнозовану роботу черг; це fixture-припущення, а не
production default. Native simulator перевіряє допустимість current requests
на Tiny/Small/Full. Packed opt-in Agent перевіряє існуючий спільний каркас.

При оцінюванні офіційним runner порівнювати заморожений V1 із замороженим
попереднім allocator на однакових сценаріях, окремо від зміни потреб/ризиків:

```text
uv run sbf compare <frozen_V1> <frozen_V4> --task=small --entropy=12345 --episodes=16 --cpu_budget=True
uv run sbf compare <frozen_V1> <frozen_V4> --task=full --entropy=12345 --episodes=4 --cpu_budget=True
```

Далі перевірити на root 67890, а root 0/dev залишити для рідкісного підтвердження.
На цьому Windows host official runner імпортує fcntl і не запускається.
Native reports — сирі витрати/CPU/clipping, не RSS і не сертифікація сервера.
Історичні числа попереднього V4 у [ALLOCATION_V4.md](ALLOCATION_V4.md) не є
результатами виправленого V1. Прогалина upstream потреб терміналів залишається
за межами цього таску: вона не приховується вигаданим fulfilment іншого вузла.

baseline, 2026-10-06:

| Tiny | 26 | 0.078125 с | 278 / 2 |
| Small | 52 | 0.125000 с | 3624 / 2 |
| Full | 104 | 0.296875 с | 34902 / 6 |

Ініціалізація врахована в першому тижні. Це локальний process CPU і видимі
clip-пари, не серверний meter. Сирі витрати baseline/V1: Tiny
2,730,599,063.80 / 2,983,847,536.85 USD; Small
2,964,621,300,056.34 / 5,168,010,190,930.98 USD; Full
5,335,791,765,444.15 / 15,151,628,946,225.86 USD. В цих smoke епізодах
V1 дорожчий; дотримання контракту і менше clipping не доводять кращу політику.
Default heuristic збережено. Точні заморожені source-файли, fingerprints та
потижнева діагностика — в outputs/10_network_allocation/2026-10-06_allocator_v1_*.

Фінальна регресія allocator, network V1/V2/V3, Agent, контрактів, analytics і
evaluation: **138 passed, 3 skipped**. Пропуски стосуються Unix Bash orchestration.
Ruff check/format і git diff --check пройшли. Статична перевірка packed opt-in
кандидата через sbf check пройшла; ізольований запуск зупинився на fcntl.

Загальний pytest з --maxfail=3 та трьома workers завершився з **24 passed,
6 failed**: усі шість помилок — наявні CLI-тести, які імпортують Unix-only
fcntl на Windows. Офіційний sbf compare також зупинився на цьому імпорті до
оцінювання. Отже, RSS-порівняння V1/V4 і повний platform suite ще не підтверджені;
native результати вище не замінюють їх.
